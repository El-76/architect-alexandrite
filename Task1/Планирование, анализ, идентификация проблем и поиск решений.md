### Анализ схемы и описания системы

#### Внешние проявления

* Клиенты жалуются менеджерам по продажам, что они не получили заказ и над их изделием работают уже несколько месяцев, хотя обещали закончить за три недели.
* После открытия API MES для приёма заказов от других продавцов жалоб от клиентов на просроченные заказы стало ещё больше.
* Добавились жалобы со стороны пользователей API. Представители компаний ежедневно сообщают, что не получили свои заказы.
* Когда операторы заходят на первую страницу MES, система долго прогружается.

#### Высокоуровневый анализ внешних проявлений - их возможные причины

Жалобы на заказы, над которыми работают несколько месяцев - скорее всего заказы не задерживаются, а где-то пропадают - нужно выяснять.

На первый взгляд можно исключить Интернет-магазин из компонент, требующих анализа в первую очередь - тк жалуются на заказы, сделанные и через Интернет-магазин и через API.

CRM может быть проблемой, тк участвует во flow заказа, если заказ не подтверждён в CRM, он выполнен не будет.

Также возможно есть проблемы во взаимодействии MES <-> CRM через Rabbit MQ.

И наконец MES - первый кандидат на исследование. Есть видимые проблемы с производительностью flow оператора, тк БД единая, причина этих проблем может влиять на работоспособность других flow - создание заказа и тп.

Также можно посмотреть на процесс расчёта стоимости - он скорее всего CPU-intensive и может влиять на flow.

Навскидку - MES не держит нагрузку (и возможно под нагрузкой возникают ошибки, которые некорректно обрабатываются, тк количество пропавших заказов растёт с ростом нагрузки) - это основная гипотеза. Ошибки могут быть разного рода - ответили ОК в API, но ничего не записали, потеряли сообщение при отправке в Rabbit, не показали операторам все заказы - операторы никогда не возьмут некоторые заказы и тп.

#### Высокоуровневый анализ архитектуры - список проблем

Есть ряд потенциальных архитектурных проблем

* Каждое приложение имеет по одному инстансу - может быть проблемой при росте нагрузки
* Базы данных имеют один инстанс, который работает на запись и на чтение - тоже может быть проблемой
* В принципе отсутствует кеширование - для каких-то кейсов оно было бы полезным
* Observability отсутствует

### Инициативы, которые необходимы для устранения нежелательных ситуаций

#### Инициативы в порядке приоритета

* Ревью кода MES (в первую очередь) и CRM - как бы ни было нагружено приложение, терять заказы оно не должно
* Настройка мониторинга - общего и с целью проверки гипотез выше
* Ревью и улучшение логгирования с целью понимания истинных причин проблем
* Настройка трейсинга

Далее всё будет зависеть от причин - репликация БД с чтением с реплик, горизонтальное масштабирование сервисов, кеширование и тп.

#### Целевая архитектура через полгода

Тяжело определить целевую архитектуру, не зная причин проблем и потенциальной нагрузки, можно только пофантазировать.

* Кеширование заказов операторов
* Горизонтально масштабируемый API MES
* БД с репликацией и чтением с реплик для use case, которые это позволяют

#### Самые важные инициативы

Первоочередные инициативы должны быть посвящены пониманию причин задержки (потерь?) заказов, есть большой соблазн начать лечить тормозящий MES для операторов, но если операторам будет некомфортно, но при этом они будут брать заказы - будет ОК на первом этапе.

* Ревью кода MES - часто быстро помогает
* Базовый мониторинг - количество заказов в разных статусах - даже можно просто поделать периодические запросы в БД - если заказы зависают в определённом статусе - будет понятен проблемный участок

Безусловных инициатив получилось всего две, а не три, далее приоритетными будет подмножество в зависимости от результатов выше:

* Мониторинг Rabbit - сколько записали, сколько прочитали и тп
* Мониторинг БД MES
* Мониторинг СPU инстанса MES (абсолют + насыщенность)
* Ревью конфигурации Rabbit
